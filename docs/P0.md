# P0 implementation plan -- data layer at production scale

Implementation plan for the P0 items from
[PerformanceRecommendations.md](PerformanceRecommendations.md):

- **P0.1** replace CsvStore internals with DuckDB serving + pluggable
  ingestion (CSV now, Azure SQL / Postgres later)
- **P0.2** drop BM25 full-text search over large datasets
  (Entitlements); keep it for the small Resources catalogue
- **P0.3** duration instrumentation on both sides of the wire

All three land as changes to `mcp-server/` plus a small
instrumentation change in `agent-client/`. The 8 CSV-backed MCP tool
CONTRACTS do not change -- the agent, its prompts, and its tests are
untouched except for timing output.

## 1. Goals and non-goals

**Goals**

- Serve `filter_dataset`, `filter_dataset_fuzzy`, `count_by_column`,
  `get_column_values`, `list_datasets` from DuckDB: indexed,
  vectorized, milliseconds at millions of rows.
- Bound memory: columnar storage on disk, buffer pool in memory --
  no more list-of-dicts of the whole dataset in Python RAM.
- Fast startup: persisted `.duckdb` file, ingest only when the source
  changed.
- Pluggable ingestion: CSV source stays (dev, tests, samples); a
  documented DatabaseSource stub reserves the prod path (Azure SQL /
  Postgres batch sync), mirroring the CsvIncidentSource /
  ServiceNowIncidentSource pattern in incident_sources.py.
- Refresh: staleness check at startup, periodic background check, and
  the reload is atomic (readers never see half-loaded data).
- Numbers: per-tool durations logged on the MCP server, per-node and
  per-turn durations in the agent's stream log.

**Non-goals (explicitly out of P0)**

- PDF/knowledgebase changes (page-level indexing is P1).
- Result caching layers (Redis) -- DuckDB latencies make them
  unnecessary; revisit only if measurements disagree.
- Implementing the actual Azure SQL / Postgres connector -- the prod
  DB is not reachable from dev; P0 ships the interface, the stub, and
  the documentation for filling it in.
- Any agent-side query or prompt changes.

## 2. Design decisions (settled)

| Decision | Choice | Reasoning |
|---|---|---|
| Serving engine | DuckDB (embedded, file-backed) | vectorized analytics, zero infra, ~10x smaller than Python dicts, spills to disk when needed; availability confirmed (duckdb 1.3.2 installs cleanly via uv) |
| Query the source DB directly instead? | No -- local DuckDB copy | protects the operational DB from bursty agent workloads; local ms latency; batch-sync matches how IGA snapshots actually refresh |
| Class/file names | keep `CsvStore` / `csv_store.py` | repo convention: MCP server internals keep implementation names; the tool contracts hide the swap |
| Full-text search | per-dataset, size-gated | BM25 stays for datasets <= MCP_SEARCH_MAX_ROWS (Resources); larger datasets get a guidance error steering to filter/count tools -- data-driven, not name-driven |
| Refresh trigger | startup staleness check + background daemon thread + reload-on-fingerprint-change | thread works for both stdio and sse transports; fingerprint check is cheap (mtime/size), reload only when changed |
| Atomicity | `CREATE OR REPLACE TABLE` inside a transaction | DuckDB readers see the old table until commit; no downtime, no partial state |
| Concurrency | one connection; `con.cursor()` per query; a write lock around refresh | FastMCP runs sync tools in a threadpool, so concurrent tool calls are real; cursors are DuckDB's supported cheap per-thread handle |
| DB file location | `MCP_DB_PATH`, default `<docs_dir>/.mcp_data.duckdb`, gitignored | lives next to the data it is derived from; delete to force full re-ingest |
| Freshness visibility | `_meta` table (dataset, fingerprint, synced_at, row_count); `list_datasets` exposes `synced_at` | the agent can tell users how fresh the data is |

## 3. Architecture

```
                 mcp-server process
                 +--------------------------------------------+
 tool calls ---> | server.py (12 tools, contracts unchanged)  |
                 |      |                                     |
                 |      v                                     |
                 | csv_store.py  CsvStore (DuckDB serving)    |
                 |      |   SQL: WHERE / regexp / GROUP BY    |
                 |      v                                     |
                 | .mcp_data.duckdb  (persisted, columnar)    |
                 |      ^                                     |
                 | data_sources.py (ingestion)                |
                 |   CsvDataSource      <- docs_dir CSVs      |
                 |   DatabaseSource     <- stub: Azure SQL /  |
                 |     (fill in later)     Postgres batch sync|
                 +--------------------------------------------+
```

**Ingestion interface** (new module `data_sources.py`):

```python
class DataSource(Protocol):
    def fingerprint(self) -> str:
        """Cheap change detector (mtimes+sizes for CSV; sync watermark
        or extract timestamp for a DB). Reload happens only when this
        differs from the stored value."""

    def load(self, con) -> list[str]:
        """(Re)create one DuckDB table per dataset inside the caller's
        transaction. Returns the dataset names loaded."""
```

- `CsvDataSource(docs_dir)`: `fingerprint()` = sorted
  `(path, mtime, size)` of `*.csv` under docs_dir, hashed. `load()` =
  `CREATE OR REPLACE TABLE <stem> AS SELECT * FROM read_csv_auto(?)`
  per file (DuckDB infers types; `all_varchar=true` to preserve
  today's everything-is-a-string semantics -- see risks).
- `DatabaseSource`: constructor takes connection string + a
  dataset->query mapping from env; `load()` documented step by step in
  the docstring (attach postgres / pyodbc fetch -> temp parquet ->
  `read_parquet`), raising NotImplementedError -- exactly the
  ServiceNowIncidentSource pattern.

**Query mapping** (CsvStore methods -> SQL):

| Method | SQL shape |
|---|---|
| `filter_rows` | `SELECT * FROM t WHERE lower(c1)=lower($1) AND ... LIMIT max+1` (the +1 detects truncation; total via `SELECT count(*)` only when truncated) |
| `filter_rows_fuzzy` | `WHERE regexp_matches(c1, $1, 'i') AND ...` |
| `count_by_column` | same WHEREs + `SELECT col AS value, count(*) AS count GROUP BY col ORDER BY count DESC` |
| `get_distinct_values` | `SELECT DISTINCT col FROM t WHERE col IS NOT NULL AND col <> '' ORDER BY col` |
| `list_datasets` | `_meta` join `information_schema.columns` (+ row_count, synced_at) |
| `search` | unchanged BM25 path, built ONLY for datasets whose row_count <= MCP_SEARCH_MAX_ROWS; otherwise `{"error": "dataset too large for free-text search -- use filter_dataset / count_by_column", ...}` |

Row results are shaped back to `list[dict]` with the same keys as
today (cursor description -> dict), `_truncated` metadata object
preserved verbatim.

## 6. Behavior changes to be aware of

1. **`search_dataset` on large datasets** (Entitlements at prod
   volume) returns a guidance error instead of BM25 results. The
   RESOURCE_PROMPT already steers the agent to `count_by_column` /
   filters for Entitlements, so agent behavior is expected to be
   unchanged in practice; the sample Entitlements CSV is far below
   the threshold anyway, so nothing changes in dev.
2. **Type inference**: `read_csv_auto` with `all_varchar=true` keeps
   every column a string, exactly matching today's semantics
   (case-insensitive string compares, string counts). Numeric typing
   is a possible later improvement, not P0.
3. **A `.duckdb` file appears** next to the data. Gitignored;
   deleting it is always safe (rebuilt from source on next start).
4. **First start after upgrade** pays one full ingest; every start
   after that is milliseconds.

## 7. Testing and verification

**Unit tests (mcp-server, no network):** build a CsvStore over tmp
CSVs and assert -- exact filter (case-insensitive), fuzzy regex filter,
AND across multiple filter columns, truncation metadata appears
beyond max_results with correct total, count_by ordering, distinct
skips empty values, search works under the threshold, search returns
the guidance error over the threshold (tiny threshold in the test),
`list_datasets` exposes columns/row_count/synced_at, invalid dataset
and column errors unchanged, refresh: touch a CSV -> fingerprint
changes -> `refresh_if_stale()` reloads (row visible) and returns
True, unchanged source returns False, persisted file reopens without
re-ingest (fingerprint match), concurrent reads during a refresh do
not error (threaded smoke test).

**Contract regression:** existing 13 auth tests keep passing; the 12
tool signatures and JSON shapes are asserted unchanged by exercising
each tool function directly against the sample docs dir.

**Scale check (scripted, not committed to CI):** generate a synthetic
5M-row entitlements CSV in the scratchpad; measure before/after for
`filter_dataset` (exact), `filter_dataset_fuzzy`, `count_by_column`,
startup time, and RSS. This produces the numbers for the acceptance
criteria below.

**Agent-side:** run the 36-test suite; assert the timing additions in
the stream file; if Azure credentials are available, run one scanner
pass as the end-to-end workload and read the new duration logs.

## 8. Acceptance criteria

Measured on the synthetic 5M-row dataset, single modest core:

| Metric | Today (expected) | Target after P0 |
|---|---|---|
| `count_by_column` with 2 exact filters | seconds | < 100 ms |
| `filter_dataset_fuzzy`, 1 regex column | seconds | < 300 ms |
| server startup, warm (unchanged source) | minutes (re-parse + BM25) | < 2 s |
| resident memory after startup | multi-GB | < 500 MB |
| tool log lines | args only | args + caller + took=ms |

If a target is missed, the numbers from P0.3 instrumentation say
where it went; do not proceed to P1 with unexplained misses.

## 9. Risks and mitigations

- **Regex dialect drift**: `filter_dataset_fuzzy` currently uses
  Python `re`; DuckDB `regexp_matches` uses RE2 syntax. The patterns
  the agent actually generates (alternations like
  `finance|accounting`, simple wildcards) are identical in both. RE2
  lacks backreferences/lookaround -- acceptable; on a regex error the
  store falls back to a literal `ILIKE %pattern%` match, mirroring
  today's escape-and-retry behavior.
- **DuckDB threading**: cursors per call + refresh lock is the
  documented safe pattern; the threaded smoke test guards it.
- **Type surprises from CSV inference**: eliminated by
  `all_varchar=true` (decision above).
- **Windows/dev parity**: DuckDB ships wheels for all target
  platforms; verified installable in this environment.
- **BM25 memory for Resources**: bounded by the row threshold; the
  Resources catalogue is orders of magnitude below it.
