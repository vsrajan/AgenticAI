## 1. Goals and non-goals

**Goals**

- Serve `filter_dataset`, `filter_dataset_fuzzy`, `count_by_column`,
  `get_column_values`, `list_datasets` from DuckDB: indexed,
  vectorized, milliseconds at millions of rows.
- Bound memory: columnar storage on disk, buffer pool in memory --
  no more list-of-dicts of the whole dataset in Python RAM.
- Fast startup: persisted `.duckdb` file, ingest only when the source
  changed.
- Pluggable ingestion: CSV source stays (dev, tests, samples); a
  documented DatabaseSource stub reserves the prod path (Azure SQL /
  Postgres batch sync), mirroring the CsvIncidentSource /
  ServiceNowIncidentSource pattern in incident_sources.py.
- Refresh: staleness check at startup, periodic background check, and
  the reload is atomic (readers never see half-loaded data).
- Numbers: per-tool durations logged on the MCP server, per-node and
  per-turn durations in the agent's stream log.

**Non-goals (explicitly out of P0)**

- PDF/knowledgebase changes (page-level indexing is P1).
- Result caching layers (Redis) -- DuckDB latencies make them
  unnecessary; revisit only if measurements disagree.
- Implementing the actual Azure SQL / Postgres connector -- the prod
  DB is not reachable from dev; P0 ships the interface, the stub, and
  the documentation for filling it in.
- Any agent-side query or prompt changes.

## 2. Design decisions (settled)

| Decision | Choice | Reasoning |
|---|---|---|
| Serving engine | DuckDB (embedded, file-backed) | vectorized analytics, zero infra, ~10x smaller than Python dicts, spills to disk when needed; availability confirmed (duckdb 1.3.2 installs cleanly via uv) |
| Query the source DB directly instead? | No -- local DuckDB copy | protects the operational DB from bursty agent workloads; local ms latency; batch-sync matches how IGA snapshots actually refresh |
| Class/file names | keep `CsvStore` / `csv_store.py` | repo convention: MCP server internals keep implementation names; the tool contracts hide the swap |
| Full-text search | per-dataset, size-gated | BM25 stays for datasets <= MCP_SEARCH_MAX_ROWS (Resources); larger datasets get a guidance error steering to filter/count tools -- data-driven, not name-driven |
| Refresh trigger | startup staleness check + background daemon thread + reload-on-fingerprint-change | thread works on every transport (stdio and the HTTP transports, streamable-http/sse); fingerprint check is cheap (mtime/size), reload only when changed |
| Atomicity | `CREATE OR REPLACE TABLE` inside a transaction | DuckDB readers see the old table until commit; no downtime, no partial state |
| Concurrency | one connection; `con.cursor()` per query; a write lock around refresh | FastMCP runs sync tools in a threadpool, so concurrent tool calls are real; cursors are DuckDB's supported cheap per-thread handle |
| DB file location | `MCP_DB_PATH`, default `<docs_dir>/.mcp_data.duckdb`, gitignored | lives next to the data it is derived from; delete to force full re-ingest |
| Freshness visibility | `_meta` table (dataset, fingerprint, synced_at, row_count); `list_datasets` exposes `synced_at` | the agent can tell users how fresh the data is |

## 3. Architecture

```
                 mcp-server process
                 +--------------------------------------------+
 tool calls ---> | server.py (12 tools, contracts unchanged)  |
                 |      |                                     |
                 |      v                                     |
                 | csv_store.py  CsvStore (DuckDB serving)    |
                 |      |   SQL: WHERE / regexp / GROUP BY    |
                 |      v                                     |
                 | .mcp_data.duckdb  (persisted, columnar)    |
                 |      ^                                     |
                 | data_sources.py (ingestion)                |
                 |   CsvDataSource      <- docs_dir CSVs      |
                 |   DatabaseSource     <- stub: Azure SQL /  |
                 |     (fill in later)     Postgres batch sync|
                 +--------------------------------------------+
```

**Ingestion interface** (new module `data_sources.py`):

```python
class DataSource(Protocol):
    def fingerprint(self) -> str:
        """Cheap change detector (mtimes+sizes for CSV; sync watermark
        or extract timestamp for a DB). Reload happens only when this
        differs from the stored value."""

    def load(self, con) -> list[str]:
        """(Re)create one DuckDB table per dataset inside the caller's
        transaction. Returns the dataset names loaded."""
```

- `CsvDataSource(docs_dir)`: `fingerprint()` = sorted
  `(path, mtime, size)` of `*.csv` under docs_dir, hashed. `load()` =
  `CREATE OR REPLACE TABLE <stem> AS SELECT * FROM read_csv_auto(?)`
  per file (DuckDB infers types; `all_varchar=true` to preserve
  today's everything-is-a-string semantics -- see risks).
- `DatabaseSource`: constructor takes connection string + a
  dataset->query mapping from env; `load()` documented step by step in
  the docstring (attach postgres / pyodbc fetch -> temp parquet ->
  `read_parquet`), raising NotImplementedError -- exactly the
  ServiceNowIncidentSource pattern.

**Query mapping** (CsvStore methods -> SQL):

| Method | SQL shape |
|---|---|
| `filter_rows` | `SELECT * FROM t WHERE lower(c1)=lower($1) AND ... LIMIT max+1` (the +1 detects truncation; total via `SELECT count(*)` only when truncated) |
| `filter_rows_fuzzy` | `WHERE regexp_matches(c1, $1, 'i') AND ...` |
| `count_by_column` | same WHEREs + `SELECT col AS value, count(*) AS count GROUP BY col ORDER BY count DESC` |
| `get_distinct_values` | `SELECT DISTINCT col FROM t WHERE col IS NOT NULL AND col <> '' ORDER BY col` |
| `list_datasets` | `_meta` join `information_schema.columns` (+ row_count, synced_at) |
| `search` | unchanged BM25 path, built ONLY for datasets whose row_count <= MCP_SEARCH_MAX_ROWS; otherwise `{"error": "dataset too large for free-text search -- use filter_dataset / count_by_column", ...}` |

Row results are shaped back to `list[dict]` with the same keys as
today (cursor description -> dict), `_truncated` metadata object
preserved verbatim.

## 6. Behavior changes to be aware of

1. **`search_dataset` on large datasets** (Entitlements at prod
   volume) returns a guidance error instead of BM25 results. The
   RESOURCE_PROMPT already steers the agent to `count_by_column` /
   filters for Entitlements, so agent behavior is expected to be
   unchanged in practice; the sample Entitlements CSV is far below
   the threshold anyway, so nothing changes in dev.
2. **Type inference**: `read_csv_auto` with `all_varchar=true` keeps
   every column a string, exactly matching today's semantics
   (case-insensitive string compares, string counts). Numeric typing
   is a possible later improvement, not P0.
3. **A `.duckdb` file appears** next to the data. Gitignored;
   deleting it is always safe (rebuilt from source on next start).
4. **First start after upgrade** pays one full ingest; every start
   after that is milliseconds.

## 9. Risks and mitigations

- **Regex dialect drift**: `filter_dataset_fuzzy` currently uses
  Python `re`; DuckDB `regexp_matches` uses RE2 syntax. The patterns
  the agent actually generates (alternations like
  `finance|accounting`, simple wildcards) are identical in both. RE2
  lacks backreferences/lookaround -- acceptable; on a regex error the
  store falls back to a literal `ILIKE %pattern%` match, mirroring
  today's escape-and-retry behavior.
- **DuckDB threading**: cursors per call + refresh lock is the
  documented safe pattern; the threaded smoke test guards it.
- **Type surprises from CSV inference**: eliminated by
  `all_varchar=true` (decision above).
- **Windows/dev parity**: DuckDB ships wheels for all target
  platforms; verified installable in this environment.
- **BM25 memory for Resources**: bounded by the row threshold; the
  Resources catalogue is orders of magnitude below it.

## 11. Switching ingestion from CSV files to a database, in detail

This section is the future runbook for the day production data stops
being CSV files and starts being an Azure SQL or Postgres database.
It assumes you have implemented P0 as described above and are
comfortable with basic Python, but have not done a data integration
like this before.

### 11.1 The mental model: only the loader changes

Keep this picture in mind the whole time:

```
TODAY (dev):    CSV files  --CsvDataSource.load()------>  DuckDB file  ---> tools
PROD:           Azure SQL  --DatabaseSource.load()----->  DuckDB file  ---> tools
                / Postgres
```

Everything to the right of the arrow is IDENTICAL in both rows. The
DuckDB file, the SQL the tools run, the 8 tool contracts, the agent,
the prompts, the tests -- none of it knows or cares where the rows
came from. The switch is: implement one class (`DatabaseSource`),
set a few environment variables, restart. That is the entire surface
area, and it is why the `DataSource` interface exists.

A second thing to internalise: this is a BATCH COPY, not a live
connection. The MCP server does not query the production database
when the agent asks a question -- it queries its own local DuckDB
copy, which a sync step refreshes on a schedule. This is deliberate
(see the design decisions in section 2): it protects the operational
database from bursty agent traffic, keeps tool latency local, and
matches how entitlement data actually changes (nightly/hourly
snapshot loads by the IGA platform, not row-by-row).

### 11.2 The interface you are filling in

`data_sources.py` defines the contract both sources implement:

```python
class DataSource(Protocol):
    def fingerprint(self) -> str: ...
    def load(self, con) -> list[str]: ...
```

Two methods, two jobs:

- **`fingerprint()` -- "has the source changed?"** Must be CHEAP,
  because the refresh sweeper calls it every few minutes. It returns
  any string that changes when the data changes. For CSVs that is
  file mtimes+sizes. For a database it must NOT be "hash all the
  rows" (that would scan millions of rows every few minutes) -- see
  11.5 for what to use instead.
- **`load(con)` -- "copy everything into DuckDB."** Called only when
  the fingerprint changed. It runs inside a transaction the store
  opens for it, creates one table per dataset with
  `CREATE OR REPLACE TABLE`, and returns the dataset names. Because
  the whole load is one transaction, agents querying mid-refresh see
  the complete OLD data until the commit, then the complete NEW data
  -- never a mixture.

### 11.3 Path A: Postgres (the easy one)

DuckDB has a first-class `postgres` extension: it can ATTACH a
running Postgres database and copy tables from it directly, server to
file, without the rows ever becoming Python objects. The core of
`DatabaseSource.load()` for Postgres is genuinely this short:

```python
def load(self, con) -> list[str]:
    con.execute("INSTALL postgres; LOAD postgres;")
    # the connection string comes from MCP_DB_CONN (see 11.6)
    con.execute(f"ATTACH '{self._conn_string}' AS src (TYPE postgres, READ_ONLY)")
    loaded = []
    for dataset_name, query in self._tables.items():   # see 11.6
        con.execute(
            f"CREATE OR REPLACE TABLE {dataset_name} AS {query}"
        )
        loaded.append(dataset_name)
    con.execute("DETACH src")
    return loaded
```

where a query in `self._tables` looks like
`SELECT * FROM src.iga.entitlements`. Five million rows copy in
seconds over a datacenter link. `READ_ONLY` is not decoration: it
guarantees this code cannot write to the source database no matter
what bug it has.

### 11.4 Path B: Azure SQL (two options)

DuckDB has no native Azure SQL scanner, so the rows need a vehicle.

**Option B1 -- Parquet as the interchange (recommended).** Do not
connect the MCP server to Azure SQL at all. Instead, let a pipeline
that already exists in most Azure shops (Azure Data Factory, Synapse,
or a scheduled `bcp`/notebook job) export the tables to **Parquet
files** on a schedule, into a folder or blob container the MCP server
can read. Parquet is a compressed columnar file format -- think "CSV
that grew up": typed, splittable, and DuckDB reads it natively and
fast:

```python
def load(self, con) -> list[str]:
    loaded = []
    for dataset_name, path in self._tables.items():   # path to .parquet
        con.execute(
            f"CREATE OR REPLACE TABLE {dataset_name} "
            f"AS SELECT * FROM read_parquet('{path}')"
        )
        loaded.append(dataset_name)
    return loaded
```

Why this is the recommended path: the MCP server needs NO database
driver, NO database credentials (file/blob access only), the export
schedule is owned by the data team with their existing tooling, and
the fingerprint is trivial (the Parquet files' mtimes -- literally
reuse `CsvDataSource.fingerprint()` pointed at `*.parquet`). If the
files live in Azure Blob Storage rather than a mounted folder,
DuckDB's `azure` extension reads `abfss://...` paths directly.

**Option B2 -- direct pull with pyodbc.** If no export pipeline
exists and you must pull from Azure SQL yourself: install `pyodbc`
plus the Microsoft ODBC driver (this is a system package, not just
pip -- the one operationally annoying part), then stream rows in
batches into DuckDB:

```python
import pyodbc

def load(self, con) -> list[str]:
    src = pyodbc.connect(self._conn_string)
    loaded = []
    for dataset_name, query in self._tables.items():
        cur = src.cursor()
        cur.execute(query)
        columns = [d[0] for d in cur.description]
        con.execute(f"DROP TABLE IF EXISTS {dataset_name}_incoming")
        con.execute(
            f"CREATE TABLE {dataset_name}_incoming "
            + "(" + ", ".join(f'"{c}" VARCHAR' for c in columns) + ")"
        )
        while True:
            batch = cur.fetchmany(50_000)      # stream, never fetchall()
            if not batch:
                break
            con.executemany(
                f"INSERT INTO {dataset_name}_incoming VALUES "
                f"({', '.join('?' for _ in columns)})", batch,
            )
        # atomic swap: build under a temp name, then replace
        con.execute(f"CREATE OR REPLACE TABLE {dataset_name} "
                    f"AS SELECT * FROM {dataset_name}_incoming")
        con.execute(f"DROP TABLE {dataset_name}_incoming")
        loaded.append(dataset_name)
    src.close()
    return loaded
```

The two novice traps here: `fetchall()` on 5M rows recreates the
memory problem P0 exists to fix (always batch), and building under an
`_incoming` name before the `CREATE OR REPLACE` keeps the swap atomic
even though the copy takes a while.

### 11.5 Fingerprints for a database

The sweeper needs a cheap "did anything change?" probe. In order of
preference:

1. **A sync-log/watermark table.** IGA batch loads usually record
   their runs (`SELECT max(run_completed_at) FROM etl_log`). One
   indexed row read; perfect fingerprint.
2. **A last-modified column:** `SELECT max(updated_at) FROM
   entitlements` -- fine IF the column is indexed.
3. **Parquet file mtimes** (option B1) -- free.
4. **Row count as a last resort** (`SELECT count(*)`) -- cheap in
   most engines but misses updates that do not change the count; only
   acceptable when loads are full snapshot replaces (count almost
   always shifts).

Never hash table contents. If the source team cannot offer any of
1-3, prefer B1's file-based flow where freshness is self-evident.

### 11.6 Configuration

New env vars (all read by `data_sources.py`, documented in
`.env.example` when this ships):

```
# which ingestion source to use: csv (default) or database
MCP_DATA_SOURCE=database

# how to reach the source. Secret -- gitignored .env only.
# Postgres:   postgresql://reader:***@dbhost:5432/iga
# Azure SQL:  Driver={ODBC Driver 18 for SQL Server};Server=...;
# Parquet:    unused (paths go in MCP_DB_TABLES)
MCP_DB_CONN=postgresql://agnes_reader:secret@dbhost:5432/iga

# dataset -> source mapping, semicolon-separated name=value pairs.
# value is a SELECT (paths for parquet). Dataset names must match what
# the prompts expect: Entitlements and Resources.
MCP_DB_TABLES=Entitlements=SELECT * FROM src.iga.entitlements;Resources=SELECT * FROM src.iga.resources

# fingerprint probe (paths/mtimes are used instead for parquet)
MCP_DB_WATERMARK=SELECT max(run_completed_at) FROM src.iga.etl_log
```

`MCP_DATA_REFRESH_MINUTES` (section 5) is reused unchanged -- it just
starts consulting the database watermark instead of CSV mtimes.

Credentials rules, same philosophy as everywhere else in this repo:
the connection string lives ONLY in the gitignored `.env`; the
database login is a dedicated READ-ONLY account (call it
`agnes_reader`) with SELECT on exactly the needed tables; on Azure,
prefer a managed identity over a password when the MCP server runs
there. Never log the connection string.

### 11.7 The actual switch, step by step

1. Confirm P0 is live and healthy on CSVs (tools answer, `synced_at`
   visible in `list_datasets`).
2. Get from the data team: read-only credentials (or the parquet drop
   location), the table/view names, and the watermark query. Ask for
   VIEWS if the raw tables have columns you do not need -- fewer
   columns = faster sync and smaller DuckDB file.
3. Implement `DatabaseSource.load()` for your path (11.3 or 11.4) --
   the stub's docstring mirrors those sections.
4. Add a test against a LOCAL database first: for Postgres, a docker
   container seeded with a few rows; for the parquet path, plain
   local files. Assert: tables land in DuckDB, row counts match,
   fingerprint changes when the seed data changes.
5. Set the env vars on the MCP server (11.6), restart. Watch the log
   for the ingest line (row counts + duration).
6. Verify through the front door: ask the agent a known entitlement
   question; check `list_datasets` shows the DB row counts and a
   fresh `synced_at`.
7. Watch one refresh cycle: bump the watermark (or wait for the next
   real load) and confirm the sweeper reloads.
8. Rollback at any point = `MCP_DATA_SOURCE=csv` + restart. The CSV
   path never went away; dev and tests use it forever.

### 11.8 What does NOT change when you switch

For emphasis, because it is the whole payoff of the design: the 12
MCP tools and their JSON shapes; the DuckDB serving SQL; the agent,
its prompts, its tests; the auth model; the refresh sweeper; the
`.duckdb` file mechanics. A future maintainer reading `csv_store.py`
cannot tell from the query code whether the rows came from a CSV or
from Azure SQL -- and that is the point.

### 11.9 IMPLEMENTED: the Parquet staging path (chosen production route)

Sections 11.3-11.5 planned a direct database pull. In practice the
production data arrived one step earlier than expected: the export
jobs (Spark/Databricks) already write each dataset as PARQUET into an
Azure Storage account. That collapses the problem -- DuckDB reads
Parquet natively (columnar file into columnar engine, its fastest
ingest path), so no database driver, no pyodbc, no ATTACH. This
section documents what was BUILT: `ParquetDataSource` in
data_sources.py, selected with `MCP_DATA_SOURCE=parquet`.

**What a Spark export actually looks like.** "Resource.parquet" in
the storage account is not a file -- it is a DIRECTORY in Spark's
standard output layout:

```
Resource.parquet/
  _SUCCESS                          <- job-completed marker (empty)
  _started_<txn id>                 <- Databricks commit-protocol markers
  _committed_<txn id>
  part-00000-tid-<hash>.parquet     <- the DATA: one file per writer task
  part-00001-tid-<hash>.parquet        (large datasets -> many parts)
```

Only the `part-*.parquet` files are data; together they form one
logical table (same schema, rows split across files). A dataset
therefore maps to a GLOB, and the `*.parquet` suffix naturally
excludes the marker files.

**Staging: blob storage -> local disk.** The DuckDB `azure` extension
can read `az://` URLs directly, but installing it needs egress to
DuckDB's extension repo -- blocked in the dev pod (HTTP 403; the
extension can be sideloaded or baked into the AKS image later, and
`ParquetDataSource` already accepts az:// URLs for that day). The
chosen v1 route needs NO extension: stage the part files locally with
az cli, authenticated as a service principal:

```bash
az login --service-principal --username <client-id> \
    --password "$AZ_SP_SECRET" --tenant <tenant-id>
az account set --subscription "<subscription>"
az storage blob download-batch \
    --account-name <account> --auth-mode login \
    --source <container> \
    --pattern 'Resource.parquet/part-*.parquet' \
    --destination ./mcp-data
```

Gotcha that catches everyone: the SP needs the DATA-PLANE role
`Storage Blob Data Reader` on the account or container --
Contributor/Owner alone do not grant blob reads via Entra auth.

**Configuration** (single mcp-server/.env, like everything else):

```
MCP_DATA_SOURCE=parquet
MCP_PARQUET_SOURCES=Resources=/abs/mcp-data/Resource.parquet/*.parquet,Entitlements=/abs/mcp-data/entitlement.parquet
```

Name=location pairs: the NAME becomes the dataset the agent sees
(decoupled from the export folder's casing), the location is a glob,
a directory (auto-expands to dir/*.parquet), a single file, or an
az:// URL. `MCP_DATA_SOURCE=csv` (the default) is the rollback and
keeps dev/tests on sample CSVs, untouched.

**Types: the one correctness decision.** Parquet columns are TYPED
(BIGINT ids, DATE grants), but the whole tool contract is
string-based -- `lower(col) = lower(?)` filters, regex matching,
BM25 over concatenated text. Ingest therefore casts every column:

```sql
CREATE OR REPLACE TABLE "Resources" AS
  SELECT COLUMNS(*)::VARCHAR FROM read_parquet('<glob>');
```

so tool behavior is byte-identical no matter what fed the table
(`filter_dataset {"UserID": "3"}` keeps working against a column that
was a BIGINT in the file). This mirrors CsvDataSource's
`all_varchar=true` and is pinned by tests.

**Fingerprints and refresh.** Same recipe as CSVs: sha256 over every
matched part file's (path, mtime, size). Re-staging a dataset --
even with a different number of parts -- triggers exactly one atomic
re-ingest on the next sweep; an empty glob contributes a "missing"
marker so data APPEARING later also triggers. az:// locations have
no change detection yet (needs blob ETags -- future); they reload on
restart only.

**Integrity note.** Spark's `_committed_` markers exist because a
failed job can leave orphan part files that a plain glob would read.
Two disciplines make that a non-issue here: copy only after
`_SUCCESS` exists, and have the export overwrite a fresh directory
each run. Revisit only if the export ever moves to append/retry
writes.
