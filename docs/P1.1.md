# P1.1 implementation plan -- page-level PDF indexing and retrieval

Implementation plan for P1.1 from
[PerformanceRecommendations.md](PerformanceRecommendations.md): index
and retrieve PDF documentation at PAGE granularity instead of whole
documents. Branch: `P1.1`, based on `Performance-P0`.

The problem this fixes: today `search_docs` ranks entire documents as
one blob, and `read_page` returns a document's ENTIRE text as one tool
result. Big documents produce huge tool results that routinely hit the
80k-character truncation in the agent -- maximum prompt-token cost
(latency AND money, on every knowledgebase turn) for clipped
information. Ranking whole documents also gets coarser as the corpus
grows: a 60-page handbook competes as one unit against a 2-page FAQ.

After P1.1: search hits point at specific PAGES, and the agent reads
just those pages (a range parameter on `read_page`). Tool results
shrink by roughly the ratio of document size to the pages actually
needed -- an order of magnitude on large documents -- and ranking
precision IMPROVES with corpus growth, because pages compete with
pages. Citations get better, not worse: the agent already cites page
numbers, and now it reads exactly what it cites.

## 1. Goals and non-goals

**Goals**

- BM25 index at page granularity: one corpus entry per non-empty PDF
  page, keyed (document, page number).
- `search_docs` results carry the specific page number of each hit,
  with the snippet taken from that page.
- `read_page` accepts an optional page selection ("3" or "2-5") and
  returns only those pages.
- Backward compatible: `read_page(path)` without a selection still
  returns the whole document, so existing prompts, the scanner, and
  any cached agent behavior keep working during migration.
- KNOWLEDGEBASE_PROMPT updated to prefer page ranges, so the token
  savings actually materialise.

**Non-goals (explicitly out of P1.1)**

- Persisting the extracted text / index to disk (that is P1.2).
- Sub-page chunking (pages are the natural citation unit here; revisit
  only if measurements show pages are still too big).
- Any change to the CSV/data tools or the quality/resource agents.

## 2. Design decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Index granularity | one BM25 entry per non-empty page | pages are the existing citation unit ([Page N] markers, prompts already cite pages); blank pages are kept in storage (numbering preserved) but not indexed |
| Search result shape | ADD a `page` field; keep `page_path`, `total_pages`, `score`, `snippet` | adding a key is contract-compatible; snippet now comes from the hit page, so it is more relevant, not just smaller |
| read_page selection syntax | `pages="N"` or `pages="N-M"` (string) | one string parameter keeps the tool schema simple for the LLM; ranges cover the "context around the hit" case; invalid input returns a structured error naming the valid forms |
| Backward compatibility | empty `pages` returns the full document | zero-risk migration; the prompt steers toward ranges, it does not force them |
| Storage | per-page text lists replace joined full text | full text is derived on demand (join); memory unchanged or better, and no duplicate storage |
| Prompt update | in the same change | without it the agent keeps requesting full documents and nothing improves; the scanner inherits the same prompt and benefits equally |

## 4. Behavior changes

1. `search_docs` results gain a `page` field and their snippets come
   from that page. Multiple pages of one document can appear as
   separate results -- that is the feature.
2. `read_page` gains an optional `pages` parameter; called without it,
   behavior is identical to before (full document).
3. The knowledgebase agent starts requesting page ranges. Answer
   quality is expected to improve (more precise context); token usage
   per knowledgebase turn drops sharply on large documents.
4. No index/storage format changes persist anywhere (P1.2 will add
   caching) -- startup still extracts PDFs each boot.

## 5. Testing

Unit tests generate small multi-page PDFs with pymupdf in tmp
directories (nothing committed): page-level search returns the correct
page number and page-local snippet; multi-page hits from one document
rank independently; read full document (no pages arg) matches the old
shape incl. [Page N] markers; read single page; read range; range
clamping errors (0, beyond total, start>end, garbage input) return
structured errors naming the valid forms; fuzzy path matching still
resolves stem/suffix; topic tree unchanged; blank pages keep numbering
(page 3 stays page 3 even if page 2 is blank).

Both existing suites must stay green: mcp-server 35 (auth + store) and
agent-client 36.
