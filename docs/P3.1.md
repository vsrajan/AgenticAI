# P3.1 implementation plan -- externalize agent session state to Redis

Implementation plan for P3.1 from
[PerformanceRecommendations.md](PerformanceRecommendations.md): move
the agent API's per-session state out of process memory and into
Redis, so that more than one agent-api instance can serve the same
sessions. Branch: `P3.1`, based on `Performance-P0` -- the migration
sequence is streamable-http -> P0 -> P3.1 -> P1.1, so `P1.1` (and
`Vector`) are rebased on top once this lands.

The problem this fixes: today AgentService keeps three things in
plain Python objects inside the one server process -- the LangGraph
checkpointer (MemorySaver: the conversation history), the session
registry (which session ids exist, when each was last used), and the
per-session asyncio locks (one turn at a time per session). Because
all three live in the process heap, a restart wipes every session and
a second instance can never see the first one's sessions. That is the
single reason the agent tier is pinned to one instance (one pod on
AKS, one uvicorn worker).

After P3.1: all three live in a Redis server that every agent-api
instance connects to over TCP. Any instance can serve any session's
next turn, restarts lose nothing that has not expired, and the agent
Deployment can scale horizontally. With `REDIS_URL` unset, behavior
is EXACTLY today's in-process MemorySaver setup -- the CLI, the
scanner, CI, and Redis-less dev never know Redis exists.

## 1. Goals and non-goals

**Goals**

- One config switch (`REDIS_URL` in the single `.env`): set -> session
  state in Redis; unset -> today's in-process behavior, byte-for-byte
  unchanged code paths for CLI/scanner/CI.
- Conversation state survives agent-api restarts (until its TTL).
- Two or more agent-api instances serve the same session pool
  correctly: any instance can run any session's next turn, and two
  simultaneous messages for one session are serialized by a
  distributed lock (never interleaved histories).
- Session hygiene semantics preserved: idle TTL, LRU cap, and the
  lock-aware "never evict a session mid-turn" rule.
- Works on PLAIN Redis 6.2+ -- no RedisJSON/RediSearch modules -- so
  the validated local redis 6.2.7 and any Azure Cache for Redis tier
  both work (see section 3).
- All existing tests stay green in the default (no-Redis) mode; new
  Redis-mode tests run against fakeredis in CI (no server needed).

**Non-goals (explicitly out of P3.1)**

- Durable conversation retention. Sessions remain EPHEMERAL --
  TTL-evicted exactly as today, just surviving restarts within the
  TTL. If an audit requirement to retain conversations appears, that
  is a separate feature (PostgresSaver or an export pipeline), and
  section 3 records the seam where it plugs in. DECISION POINT for
  review: confirm ephemeral is the requirement.
- Checkpoint pruning / growth bounding (P3.2). Noted in section 13;
  the TTL bounds total growth in the meantime.
- AKS manifests, HPA config, Azure Cache provisioning (deployment
  work, not code; see section 12 for what the code guarantees).
- Multi-worker uvicorn in one pod. Scale-out unit stays one process
  per instance; you add instances (pods), not workers.
- CLI/scanner changes: they keep in-process MemorySaver forever --
  a single interactive process gains nothing from Redis.

## 2. Design decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Store | one shared Redis (managed Azure Cache in prod; local redis-server in dev) | the standard externalized-session store; per-key TTL and atomic NX writes map 1:1 onto our registry and locks; validated locally 2026-07-14 |
| Checkpointer | custom minimal `RedisSaver` on PLAIN Redis strings | the official langgraph-checkpoint-redis needs RedisJSON/RediSearch modules (redis-stack locally, Azure Cache ENTERPRISE tier in prod); our usage is narrow enough that a small saver is the better trade -- full analysis in section 3 |
| Serialization | langgraph's own `JsonPlusSerializer` | the same serde MemorySaver uses; LangChain message objects round-trip without custom code |
| Registry | one Redis hash per session + a ZSET index scored by last-used | hash carries the metadata and gets `EXPIRE` (idle TTL enforces itself server-side; the sweeper loop disappears in Redis mode); the ZSET gives the LRU cap an O(log n) "who is oldest" lookup |
| Locks | `SET lock:{id} <token> NX PX <timeout>` via redis-py's built-in asyncio `Lock` | the standard single-Redis distributed lock; token-checked release so an expired lock is never released by the wrong holder; PX timeout means a crashed pod's lock frees itself |
| Lock timeout | `AGENT_API_LOCK_TIMEOUT_SECONDS`, default 300 | must exceed the longest realistic turn (LLM retries included) or a slow turn's lock expires mid-turn; 5 minutes is ~10x a bad turn today |
| Seam in code | a small `SessionStore` interface with two implementations: `InMemorySessionStore` (extracted current behavior) and `RedisSessionStore` | AgentService stops owning the sessions dict directly; everything else in agent_api.py (stream/ask/history/endpoints) is untouched; the checkpointer already has its seam (constructor parameter) |
| Config seam | `REDIS_URL` in the single agent-client `.env` | matches the house pattern (one env file, absent = old behavior); `rediss://` URLs give TLS for Azure Cache with zero extra code |
| Key namespace | `agnes:` prefix on every key | several apps can share one Redis; `agnes:*` makes ours identifiable and cleanly deletable |

## 3. The checkpointer decision, in detail

LangGraph persists conversation state through a checkpointer object.
The compiled graph calls it on every superstep; AgentService calls
`aget_state` (read latest) and `delete_thread` (evict). Three ways to
back it with something out-of-process:

**Option A -- custom minimal RedisSaver on plain Redis (CHOSEN).**
Subclass `langgraph.checkpoint.base.BaseCheckpointSaver` and
implement the interface against plain string keys (verified against
the installed langgraph 1.0.8: `aput`, `aget_tuple`, `alist`,
`aput_writes`, `adelete_thread`, plus `get_next_version`; sync
variants delegate or raise, since the API server is async-only).
Serialization via langgraph's `JsonPlusSerializer` -- the same one
MemorySaver uses, so message objects round-trip identically.

- For: works on the validated plain redis 6.2.7 AND every Azure Cache
  tier; no second datastore; checkpoint keys inherit the same TTL
  discipline as the session (state and registry can never disagree
  for long); smallest operational footprint.
- Against: we own its correctness. Mitigated by how little of the
  interface our usage exercises: latest-checkpoint reads, sequential
  writes from a single locked turn, thread deletion, and `alist` only
  over one thread's checkpoints. No time-travel, no branching, no
  cross-thread queries. The unit tests in section 9 pin exactly these
  behaviors.

**Option B -- official langgraph-checkpoint-redis.** Maintained by
Redis Inc., but requires the RedisJSON + RediSearch modules: locally
that means redis-stack (extra friction on the RHEL 8 dev pod whose
repos are already awkward), and on Azure it restricts you to the
Enterprise tier. Paying an infrastructure-tier constraint to avoid
~200 lines of pinned-down code is the wrong trade here.

**Option C -- official PostgresSaver.** Battle-tested and durable,
but introduces a second store (registry/locks still want Redis),
plus local/prod Postgres provisioning. Right answer IF conversations
must be durably retained (audit trail); wrong default for ephemeral
TTL-bound sessions. If the retention requirement lands later, the
checkpointer constructor parameter is the seam: swap `RedisSaver`
for `PostgresSaver` without touching the registry or locks.

## 4. Architecture and key layout

```
            load balancer (plain -- no stickiness needed)
                |                |
        agent-api instance A   agent-api instance B    (N instances)
                |                |
                +------ Redis ---+        all keys under agnes:
```

Keys (all with the session's idle TTL, refreshed on every touch):

| Key | Type | Holds |
|---|---|---|
| `agnes:session:{id}` | hash | owner subject, created_at, last_used (informational; expiry is the real TTL) |
| `agnes:sessions:index` | zset | member = session id, score = last_used epoch -- the LRU index |
| `agnes:lock:{id}` | string | the turn lock (redis-py Lock token), PX = lock timeout |
| `agnes:ckpt:{thread}:{checkpoint_id}` | string | one serialized checkpoint |
| `agnes:ckpt-index:{thread}` | zset | checkpoint ids in order -- latest-lookup and alist |
| `agnes:ckpt-writes:{thread}:{checkpoint_id}` | hash | pending writes for that checkpoint (aput_writes) |

Notes:

- The ZSET index entries cannot carry a TTL themselves (only whole
  keys expire), so reads treat the hash as the source of truth: if
  `agnes:session:{id}` is gone, the session is expired regardless of
  a stale index entry, and the reader removes the stale entry lazily.
- `delete_thread` removes every `agnes:ckpt*:{thread}*` key; eviction
  therefore frees Redis memory the same way it frees process memory
  today.
- No sweeper task in Redis mode: `EXPIRE` does the idle-TTL job
  server-side. (The in-memory mode keeps its existing sweeper.)

## 5. Turn lifecycle with Redis

```
POST /sessions/{id}/messages(/stream)
  1. registry.require(id)      -> HGETALL agnes:session:{id}
                                  missing -> 404 (as today)
                                  found   -> refresh EXPIRE + zset score
  2. lock = Lock(agnes:lock:{id}, timeout=300s); await lock.acquire()
                                  second turn for the same session
                                  waits here, even on another instance
  3. run the graph             -> checkpointer reads latest checkpoint,
                                  writes new ones as supersteps commit
                                  (each write refreshes the ckpt TTLs)
  4. finally: lock.release()   -> token-checked; if the lock expired
                                  mid-turn, log a warning (see risks)
```

Eviction paths:

- Idle TTL: keys expire server-side; the next request 404s and the
  web client already auto-recreates.
- LRU cap on create: `ZRANGE agnes:sessions:index 0 0` -> oldest id;
  skip it if `EXISTS agnes:lock:{oldest}` (turn in flight -- the
  lock-aware rule, same as today); else delete its keys.

## 7. Configuration

All in the single `agent-client/.env`:

| Variable | Default | Meaning |
|---|---|---|
| `REDIS_URL` | unset | unset -> in-process MemorySaver behavior, exactly as today. Set -> registry, locks, and checkpoints in Redis |
| `AGENT_API_LOCK_TIMEOUT_SECONDS` | `300` | distributed turn-lock TTL; must exceed the longest realistic turn |
| `AGENT_API_SESSION_TTL_MINUTES` | `60` | unchanged meaning; in Redis mode it becomes the keys' EXPIRE |
| `AGENT_API_MAX_SESSIONS` | `500` | unchanged meaning; enforced via the LRU zset in Redis mode |

`REDIS_URL` forms -- the URL is the ONLY thing that changes between
environments (everything rides in it: password, TLS, port, db):

| Environment | URL |
|---|---|
| local dev, no auth (validated rig) | `redis://localhost:6379/0` |
| shared dev box, password | `redis://:S0meP@ss@redis-dev.internal:6379/0` |
| Azure Cache for Redis (prod) | `rediss://:<access-key>@<name>.redis.cache.windows.net:6380/0` |

Notes: the `:password@` form has an empty username (classic
requirepass / Azure access-key auth); Redis 6+ ACL users go
`redis://user:pass@...`; the extra `s` in `rediss://` switches
redis-py to TLS from the URL alone (Azure Cache enforces TLS on
6380). The URL contains a secret, so it is never logged (startup
logs name the HOST only) and never committed -- real value in the
gitignored .env, Kubernetes Secret on AKS.

## 8. Behavior changes

1. With `REDIS_URL` unset: none. Same objects, same tests, same
   sweeper. This is the default and stays the CLI/scanner/CI mode.
2. With Redis: sessions survive agent-api restarts until idle TTL;
   an instance restart mid-turn loses that turn (client got a 500 or
   a dropped stream) but the session continues on retry.
3. Two messages for one session sent to two instances: the second
   waits on the distributed lock -- same serialization the asyncio
   lock gave inside one process.
4. A crashed instance's lock self-expires after the lock timeout;
   that session is usable again within 5 minutes worst-case (today a
   crash loses the session entirely, so this is strictly better).
5. Turn latency gains a few Redis round-trips (~0.5-1 ms each,
   in-cluster): registry touch, lock acquire/release, one checkpoint
   write per superstep. Milliseconds per turn against seconds of LLM
   time.
6. `GET /sessions/{id}/messages` (history) in Redis mode reads state
   written by ANY instance -- debugging works across the fleet.

## 11. Rollout and rollback

- Ship with `REDIS_URL` unset -> nothing changes anywhere.
- Dev validation: local redis + the two-instance rig.
- Prod: Azure Cache for Redis (any tier -- plain commands only),
  `rediss://` URL with the access key, set on every agent replica;
  then and only then raise replicas above 1.
- Rollback: unset `REDIS_URL` AND drop replicas to 1 in the same
  action -- in-process mode with multiple replicas is the one
  forbidden combination (each replica would have private sessions
  behind one load balancer).

## 12. AKS notes

- Any Azure Cache tier works (the plain-Redis decision exists for
  exactly this reason); TLS via rediss:// -- redis-py handles it from
  the URL alone.
- Readiness probe should include a Redis PING once REDIS_URL is set:
  an instance that cannot reach Redis must not receive traffic
  (/health returns 503 when the ping fails).
- The load balancer stays plain round-robin: no session affinity, no
  sticky cookies -- cross-instance continuity is the feature.
- Secret handling: the Redis access key rides in REDIS_URL, so the
  URL belongs in a Kubernetes secret (Key Vault CSI), not a ConfigMap.
- Auth ladder for reference (connection-time, not per-request):
  none+localhost (dev only; protected-mode blocks remote) -> password
  / Azure access key (`:key@` in the URL; primary/secondary keys
  rotate like the MCP bearer tokens) -> Redis 6 ACL users (scoped to
  `agnes:*` keys on a shared Redis) -> TLS (`rediss://`, orthogonal,
  prod always) -> Entra ID token auth via managed identity (Azure
  Cache supports it; needs a redis-py credential provider instead of
  a bare URL -- future item on the existing Entra roadmap, not P3.1).

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Redis down = agent down (new hard dependency) | fail-fast startup + readiness probe; managed Redis with replication in prod; rollback is one env change |
| lock expires under a pathologically slow turn -> second turn could interleave | 300s default is ~10x a bad turn; timeout env-tunable; release logs a loud warning when the token is gone so occurrences are visible; P4's uvloop and P1.3's trimming both shorten turns |
| custom RedisSaver correctness | narrow contract (section 3) pinned by unit tests incl. graph-level round-trip and restart simulation; PostgresSaver remains a drop-in escape hatch via the constructor seam |
| checkpoint volume (full state per superstep, now over the network) | TTL bounds total footprint; P3.2 (pruning) is the follow-up; measured overhead recorded in acceptance |
| stale LRU index entries after TTL expiry | hash is source of truth; lazy cleanup on read (tested) |
