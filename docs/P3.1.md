# P3.1 implementation plan -- externalize agent session state to Redis

Implementation plan for P3.1 from
[PerformanceRecommendations.md](PerformanceRecommendations.md): move
the agent API's per-session state out of process memory and into
Redis, so that more than one agent-api instance can serve the same
sessions. Branch: `P3.1`, based on `P1.1` -- the migration sequence
was reordered (2026-07-15) to streamable-http -> P0 -> P1.1 -> P3.1,
because P3.1 is blocked on shared-Redis infrastructure (a proper AKS
dev cluster); P1.1 moved ahead so it can ship first. `Vector` (a
docs-only plan) rebases on top.

The problem this fixes: today AgentService keeps three things in
plain Python objects inside the one server process -- the LangGraph
checkpointer (MemorySaver: the conversation history), the session
registry (which session ids exist, when each was last used), and the
per-session asyncio locks (one turn at a time per session). Because
all three live in the process heap, a restart wipes every session and
a second instance can never see the first one's sessions. That is the
single reason the agent tier is pinned to one instance (one pod on
AKS, one uvicorn worker).

After P3.1: all three live in a Redis server that every agent-api
instance connects to over TCP. Any instance can serve any session's
next turn, restarts lose nothing that has not expired, and the agent
Deployment can scale horizontally. With `REDIS_URL` unset, behavior
is EXACTLY today's in-process MemorySaver setup -- the CLI, the
scanner, CI, and Redis-less dev never know Redis exists.

## 1. Goals and non-goals

**Goals**

- One config switch (`REDIS_URL` in the single `.env`): set -> session
  state in Redis; unset -> today's in-process behavior, byte-for-byte
  unchanged code paths for CLI/scanner/CI.
- Conversation state survives agent-api restarts (until its TTL).
- Two or more agent-api instances serve the same session pool
  correctly: any instance can run any session's next turn, and two
  simultaneous messages for one session are serialized by a
  distributed lock (never interleaved histories).
- Session hygiene semantics preserved: idle TTL, LRU cap, and the
  lock-aware "never evict a session mid-turn" rule.
- Works on PLAIN Redis 6.2+ -- no RedisJSON/RediSearch modules -- so
  the validated local redis 6.2.7 and any Azure Cache for Redis tier
  both work (see section 3).
- All existing tests stay green in the default (no-Redis) mode; new
  Redis-mode tests run against fakeredis in CI (no server needed).

**Non-goals (explicitly out of P3.1)**

- Durable conversation retention. Sessions remain EPHEMERAL --
  TTL-evicted exactly as today, just surviving restarts within the
  TTL. If an audit requirement to retain conversations appears, that
  is a separate feature (PostgresSaver or an export pipeline), and
  section 3 records the seam where it plugs in. DECISION POINT for
  review: confirm ephemeral is the requirement.
- Checkpoint pruning / growth bounding (P3.2). Noted in section 13;
  the TTL bounds total growth in the meantime.
- AKS manifests, HPA config, Azure Cache provisioning (deployment
  work, not code; see section 12 for what the code guarantees).
- Multi-worker uvicorn in one pod. Scale-out unit stays one process
  per instance; you add instances (pods), not workers.
- CLI/scanner changes: they keep in-process MemorySaver forever --
  a single interactive process gains nothing from Redis.

## 2. Design decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Store | one shared Redis (managed Azure Cache in prod; local redis-server in dev) | the standard externalized-session store; per-key TTL and atomic NX writes map 1:1 onto our registry and locks; validated locally 2026-07-14 |
| Checkpointer | custom minimal `RedisSaver` on PLAIN Redis strings | the official langgraph-checkpoint-redis needs RedisJSON/RediSearch modules (redis-stack locally, Azure Cache ENTERPRISE tier in prod); our usage is narrow enough that a small saver is the better trade -- full analysis in section 3 |
| Serialization | langgraph's own `JsonPlusSerializer` | the same serde MemorySaver uses; LangChain message objects round-trip without custom code |
| Registry | one Redis hash per session + a ZSET index scored by last-used | hash carries the metadata and gets `EXPIRE` (idle TTL enforces itself server-side; the sweeper loop disappears in Redis mode); the ZSET gives the LRU cap an O(log n) "who is oldest" lookup |
| Locks | `SET lock:{id} <token> NX PX <timeout>` via redis-py's built-in asyncio `Lock` | the standard single-Redis distributed lock; token-checked release so an expired lock is never released by the wrong holder; PX timeout means a crashed pod's lock frees itself |
| Lock timeout | `AGENT_API_LOCK_TIMEOUT_SECONDS`, default 300 | must exceed the longest realistic turn (LLM retries included) or a slow turn's lock expires mid-turn; 5 minutes is ~10x a bad turn today |
| Seam in code | a small `SessionStore` interface with two implementations: `InMemorySessionStore` (extracted current behavior) and `RedisSessionStore` | AgentService stops owning the sessions dict directly; everything else in agent_api.py (stream/ask/history/endpoints) is untouched; the checkpointer already has its seam (constructor parameter) |
| Config seam | `REDIS_URL` in the single agent-client `.env` | matches the house pattern (one env file, absent = old behavior); `rediss://` URLs give TLS for Azure Cache with zero extra code |
| Key namespace | `agnes:` prefix on every key | several apps can share one Redis; `agnes:*` makes ours identifiable and cleanly deletable |

## 3. The checkpointer decision, in detail

LangGraph persists conversation state through a checkpointer object.
The compiled graph calls it on every superstep; AgentService calls
`aget_state` (read latest) and `delete_thread` (evict). Three ways to
back it with something out-of-process:

**Option A -- custom minimal RedisSaver on plain Redis (CHOSEN).**
Subclass `langgraph.checkpoint.base.BaseCheckpointSaver` and
implement the interface against plain string keys (verified against
the installed langgraph 1.0.8: `aput`, `aget_tuple`, `alist`,
`aput_writes`, `adelete_thread`, plus `get_next_version`; sync
variants delegate or raise, since the API server is async-only).
Serialization via langgraph's `JsonPlusSerializer` -- the same one
MemorySaver uses, so message objects round-trip identically.

- For: works on the validated plain redis 6.2.7 AND every Azure Cache
  tier; no second datastore; checkpoint keys inherit the same TTL
  discipline as the session (state and registry can never disagree
  for long); smallest operational footprint.
- Against: we own its correctness. Mitigated by how little of the
  interface our usage exercises: latest-checkpoint reads, sequential
  writes from a single locked turn, thread deletion, and `alist` only
  over one thread's checkpoints. No time-travel, no branching, no
  cross-thread queries. The unit tests in section 9 pin exactly these
  behaviors.

**Option B -- official langgraph-checkpoint-redis.** Maintained by
Redis Inc., but requires the RedisJSON + RediSearch modules: locally
that means redis-stack (extra friction on the RHEL 8 dev pod whose
repos are already awkward), and on Azure it restricts you to the
Enterprise tier. Paying an infrastructure-tier constraint to avoid
~200 lines of pinned-down code is the wrong trade here.

**Option C -- official PostgresSaver.** Battle-tested and durable,
but introduces a second store (registry/locks still want Redis),
plus local/prod Postgres provisioning. Right answer IF conversations
must be durably retained (audit trail); wrong default for ephemeral
TTL-bound sessions. If the retention requirement lands later, the
checkpointer constructor parameter is the seam: swap `RedisSaver`
for `PostgresSaver` without touching the registry or locks.

## 4. Architecture and key layout

```
            load balancer (plain -- no stickiness needed)
                |                |
        agent-api instance A   agent-api instance B    (N instances)
                |                |
                +------ Redis ---+        all keys under agnes:
```

Keys (all with the session's idle TTL, refreshed on every touch):

| Key | Type | Holds |
|---|---|---|
| `agnes:session:{id}` | hash | owner subject, created_at, last_used (informational; expiry is the real TTL) |
| `agnes:sessions:index` | zset | member = session id, score = last_used epoch -- the LRU index |
| `agnes:lock:{id}` | string | the turn lock (redis-py Lock token), PX = lock timeout |
| `agnes:ckpt:{thread}:{checkpoint_id}` | string | one serialized checkpoint |
| `agnes:ckpt-index:{thread}` | zset | checkpoint ids in order -- latest-lookup and alist |
| `agnes:ckpt-writes:{thread}:{checkpoint_id}` | hash | pending writes for that checkpoint (aput_writes) |

Notes:

- The ZSET index entries cannot carry a TTL themselves (only whole
  keys expire), so reads treat the hash as the source of truth: if
  `agnes:session:{id}` is gone, the session is expired regardless of
  a stale index entry, and the reader removes the stale entry lazily.
- `delete_thread` removes every `agnes:ckpt*:{thread}*` key; eviction
  therefore frees Redis memory the same way it frees process memory
  today.
- No sweeper task in Redis mode: `EXPIRE` does the idle-TTL job
  server-side. (The in-memory mode keeps its existing sweeper.)

## 5. Turn lifecycle with Redis

```
POST /sessions/{id}/messages(/stream)
  1. registry.require(id)      -> HGETALL agnes:session:{id}
                                  missing -> 404 (as today)
                                  found   -> refresh EXPIRE + zset score
  2. lock = Lock(agnes:lock:{id}, timeout=300s); await lock.acquire()
                                  second turn for the same session
                                  waits here, even on another instance
  3. run the graph             -> checkpointer reads latest checkpoint,
                                  writes new ones as supersteps commit
                                  (each write refreshes the ckpt TTLs)
  4. finally: lock.release()   -> token-checked; if the lock expired
                                  mid-turn, log a warning (see risks)
```

Eviction paths:

- Idle TTL: keys expire server-side; the next request 404s and the
  web client already auto-recreates.
- LRU cap on create: `ZRANGE agnes:sessions:index 0 0` -> oldest id;
  skip it if `EXISTS agnes:lock:{oldest}` (turn in flight -- the
  lock-aware rule, same as today); else delete its keys.

## 7. Configuration

All in the single `agent-client/.env`:

| Variable | Default | Meaning |
|---|---|---|
| `REDIS_URL` | unset | unset -> in-process MemorySaver behavior, exactly as today. Set -> registry, locks, and checkpoints in Redis |
| `AGENT_API_LOCK_TIMEOUT_SECONDS` | `300` | distributed turn-lock TTL; must exceed the longest realistic turn |
| `AGENT_API_SESSION_TTL_MINUTES` | `60` | unchanged meaning; in Redis mode it becomes the keys' EXPIRE |
| `AGENT_API_MAX_SESSIONS` | `500` | unchanged meaning; enforced via the LRU zset in Redis mode |

`REDIS_URL` forms -- the URL is the ONLY thing that changes between
environments (everything rides in it: password, TLS, port, db):

| Environment | URL |
|---|---|
| local dev, no auth (validated rig) | `redis://localhost:6379/0` |
| shared dev box, password | `redis://:S0meP@ss@redis-dev.internal:6379/0` |
| Azure Cache for Redis (prod) | `rediss://:<access-key>@<name>.redis.cache.windows.net:6380/0` |

Notes: the `:password@` form has an empty username (classic
requirepass / Azure access-key auth); Redis 6+ ACL users go
`redis://user:pass@...`; the extra `s` in `rediss://` switches
redis-py to TLS from the URL alone (Azure Cache enforces TLS on
6380). The URL contains a secret, so it is never logged (startup
logs name the HOST only) and never committed -- real value in the
gitignored .env, Kubernetes Secret on AKS.

## 8. Behavior changes

1. With `REDIS_URL` unset: none. Same objects, same tests, same
   sweeper. This is the default and stays the CLI/scanner/CI mode.
2. With Redis: sessions survive agent-api restarts until idle TTL;
   an instance restart mid-turn loses that turn (client got a 500 or
   a dropped stream) but the session continues on retry.
3. Two messages for one session sent to two instances: the second
   waits on the distributed lock -- same serialization the asyncio
   lock gave inside one process.
4. A crashed instance's lock self-expires after the lock timeout;
   that session is usable again within 5 minutes worst-case (today a
   crash loses the session entirely, so this is strictly better).
5. Turn latency gains a few Redis round-trips (~0.5-1 ms each,
   in-cluster): registry touch, lock acquire/release, one checkpoint
   write per superstep. Milliseconds per turn against seconds of LLM
   time.
6. `GET /sessions/{id}/messages` (history) in Redis mode reads state
   written by ANY instance -- debugging works across the fleet.

### 9.1 The same rig behind a real load balancer (nginx)

The rig above proves cross-instance continuity by MANUALLY choosing
which instance serves each request. Putting a real load balancer in
front closes the gap to production: both HTML clients point at ONE
URL, every request lands on whichever instance round-robin picks, and
nothing about the session can depend on instance choice. This is the
closest local approximation of the AKS ingress -- and nginx is the
right proxy to use, because the cluster's ingress controller IS
nginx: the SSE settings below are the same two knobs the Helm chart
sets as ingress annotations (deploy.md section 5).

**Install** (RHEL 8). nginx, like redis, is a "modular" AppStream
package, and on a machine wearing CentOS 8 repos dnf refuses modular
RPMs with `No available modular metadata`. Same workaround as the
redis install -- tell dnf to treat the repo's packages as ordinary
RPMs:

```bash
sudo dnf install -y nginx --setopt=centos-8-appstream.module_hotfixes=true
nginx -v
```

(Adjust the repo id to whatever `dnf repolist` shows. And remember
the machine is a POD: dnf installs land on the ephemeral container
filesystem and vanish when the pod is recreated. Either re-run the
install after a restart, or keep a bootstrap line in `~/.bashrc` --
home persists: `command -v nginx >/dev/null || sudo dnf install -y
nginx --setopt=centos-8-appstream.module_hotfixes=true`.)

**Configure.** No root and no /etc/nginx needed -- nginx runs as your
user with a self-contained config on a high port. Save as `lb.conf`
in an empty directory (say `~/lb/`):

```nginx
# lb.conf -- round-robin over two local agent-api instances, SSE-safe
worker_processes 1;
pid nginx-lb.pid;
error_log nginx-lb-error.log;

events { worker_connections 128; }

http {
    access_log nginx-lb-access.log;

    # keep all temp paths local so no root-owned dirs are needed
    client_body_temp_path tmp;
    proxy_temp_path       tmp;
    fastcgi_temp_path     tmp;
    uwsgi_temp_path       tmp;
    scgi_temp_path        tmp;

    upstream agent_api {
        # round-robin is the default -- no directive needed.
        # deliberately NO stickiness: that is the P3.1 claim under test.
        server 127.0.0.1:8080;
        server 127.0.0.1:8081;
    }

    server {
        listen 9000;

        location / {
            proxy_pass http://agent_api;
            proxy_http_version 1.1;
            proxy_set_header Connection "";

            # the two settings the AKS ingress annotations map to:
            proxy_buffering off;        # SSE: forward each token as it arrives
            proxy_read_timeout 300s;    # a full turn (matches the lock timeout)
            proxy_send_timeout 300s;
        }
    }
}
```

**Run and verify:**

```bash
cd ~/lb && mkdir -p tmp
nginx -p "$PWD" -c lb.conf -g 'daemon off;'    # foreground; ctrl-c stops it
```

One cosmetic alert at startup is expected: `could not open error log
file ... /var/log/nginx/error.log ... Permission denied`. nginx
probes its compile-time default log path BEFORE reading the config;
one line later it switches to the local `nginx-lb-error.log` and
never touches /var/log again. Ignore it (or, on nginx >= 1.19.5, add
`-e nginx-lb-error.log` to suppress it at the source).

Point BOTH html clients at `http://<host>:9000` and re-run rig tests
1-3 without choosing instances by hand -- the balancer chooses now.
What to check:

```bash
# requests alternate between instances (nginx balances per REQUEST,
# not per connection, so even one keep-alive browser gets spread):
for i in 1 2 3 4; do curl -s http://localhost:9000/health > /dev/null; done
# -> the hits alternate across the two uvicorn terminals

# a multi-turn conversation through :9000 shows turns of ONE session
# served by BOTH instances -- watch stream_a.txt vs stream_b.txt --
# with full context every turn. That is the P3.1 payoff end to end:
# session id in the URL path, everything else keyed off it in Redis.
```

Worth two extra minutes while the rig is up -- comment out
`proxy_buffering off;`, restart nginx, and use the streaming client:
tokens stop trickling and arrive as one lump at the end of the turn.
That silent lump is the #1 "works locally, breaks on AKS" trap
(aks.md section 6), and this directive is exactly what the chart's
`nginx.ingress.kubernetes.io/proxy-buffering: "off"` annotation sets
cluster-side. Re-enable and streaming returns.

## 11. Rollout and rollback

- Ship with `REDIS_URL` unset -> nothing changes anywhere.
- Dev validation: local redis + the two-instance rig.
- Prod: Azure Cache for Redis (any tier -- plain commands only),
  `rediss://` URL with the access key, set on every agent replica;
  then and only then raise replicas above 1.
- Rollback: unset `REDIS_URL` AND drop replicas to 1 in the same
  action -- in-process mode with multiple replicas is the one
  forbidden combination (each replica would have private sessions
  behind one load balancer).

## 12. AKS notes

- Any Azure Cache tier works (the plain-Redis decision exists for
  exactly this reason); TLS via rediss:// -- redis-py handles it from
  the URL alone.
- Readiness probe should include a Redis PING once REDIS_URL is set:
  an instance that cannot reach Redis must not receive traffic
  (/health returns 503 when the ping fails).
- The load balancer stays plain round-robin: no session affinity, no
  sticky cookies -- cross-instance continuity is the feature.
- Secret handling: the Redis access key rides in REDIS_URL, so the
  URL belongs in a Kubernetes secret (Key Vault CSI), not a ConfigMap.
- Auth ladder for reference (connection-time, not per-request):
  none+localhost (dev only; protected-mode blocks remote) -> password
  / Azure access key (`:key@` in the URL; primary/secondary keys
  rotate like the MCP bearer tokens) -> Redis 6 ACL users (scoped to
  `agnes:*` keys on a shared Redis) -> TLS (`rediss://`, orthogonal,
  prod always) -> Entra ID token auth via managed identity (Azure
  Cache supports it; needs a redis-py credential provider instead of
  a bare URL -- future item on the existing Entra roadmap, not P3.1).

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Redis down = agent down (new hard dependency) | fail-fast startup + readiness probe; managed Redis with replication in prod; rollback is one env change |
| lock expires under a pathologically slow turn -> second turn could interleave | 300s default is ~10x a bad turn; timeout env-tunable; release logs a loud warning when the token is gone so occurrences are visible; P4's uvloop and P1.3's trimming both shorten turns |
| custom RedisSaver correctness | narrow contract (section 3) pinned by unit tests incl. graph-level round-trip and restart simulation; PostgresSaver remains a drop-in escape hatch via the constructor seam |
| checkpoint volume (full state per superstep, now over the network) | TTL bounds total footprint; P3.2 (pruning) is the follow-up; measured overhead recorded in acceptance |
| stale LRU index entries after TTL expiry | hash is source of truth; lazy cleanup on read (tested) |

## 14. The turn-lock timeout, in detail

`AGENT_API_LOCK_TIMEOUT_SECONDS` (default 300) is the TTL on the
distributed turn lock -- the one genuinely subtle parameter in this
feature. This section explains what it protects, what happens at its
edges, and how to size it.

### What exactly is "one turn"?

The lock is acquired right after session validation in stream() and
held for the ENTIRE body of one turn -- everything a single user
message triggers:

```
user message
  -> router LLM call
  -> specialist LLM call(s)
  -> tool-loop iterations (MCP calls), as many as the turn needs
  -> final LLM response, streamed token by token to the client
  -> stream-file logging, TTL touch
release
```

One user message = one lock hold = one turn. Note one subtlety:
stream() is an async generator feeding the SSE response, so tokens are
yielded to the client WHILE the lock is held -- a pathologically
slow-reading client stretches the hold time beyond pure LLM + tool
time. One more reason the default carries ~10x headroom.

### Why the in-process lock never needed a timeout

The old asyncio.Lock lives inside the server process. If the process
crashes mid-turn, the lock dies WITH it -- a lock and its holder share
a fate, so "held forever by a ghost" is impossible by construction.

### Why a distributed lock must have one

The Redis lock is just a key (agnes:lock:{session_id}) in a DIFFERENT
process. If instance A acquires it and then crashes mid-turn (OOM,
pod eviction), A is gone but the key it wrote is still in Redis, and
nothing will ever release it. Every future message for that session,
on every instance, would wait forever: the session is permanently
bricked. The PX timeout is the escape hatch -- Redis deletes an
unreleased key when the TTL elapses. So the setting's real meaning is:
"how long after an instance crashes mid-turn does that one session
stay locked out?" (Strictly better than the in-memory behavior, where
a crash loses the session entirely.)

### The tension: why it must exceed the longest realistic turn

The TTL cannot distinguish "holder is dead" from "holder is alive but
slow", and the two failure directions are NOT symmetric:

- Too long (say an hour): a crashed instance's session stays bricked
  for an hour. Bounded inconvenience, rare.
- Too short (say 30s): a LEGITIMATE long turn -- Azure OpenAI retries
  after 429s, a tool-heavy audit turn -- has its lock expire while
  still running. A second message for the same session can then start
  a second turn CONCURRENTLY with the first, and both write into one
  LangGraph thread: exactly the interleaved-history corruption the
  lock exists to prevent. Silent correctness loss.

Hence the sizing rule: comfortably above the longest PLAUSIBLE turn,
not the average. Typical turns run 5-30s; a pathological one might
reach 60s; 300s is ~10x the bad case.

### The safety nets at the edge

1. Token-checked release. Each acquisition stores a unique token in
   the key; release (a Lua script inside redis-py's Lock) deletes the
   key only if the token still matches. Without this, a turn whose
   lock expired would, on finishing, delete the NEXT turn's lock and
   cascade the failure. With it, the stale release is simply refused.
2. The refused release logs loudly instead of raising:
   "turn lock for session ... expired before release -- consider
   raising AGENT_API_LOCK_TIMEOUT_SECONDS". The turn already
   completed; failing it retroactively helps no one. This log line is
   the TUNING SIGNAL: seen occasionally -> raise the value; never
   seen -> sized correctly. (A test pins this behavior: expire the
   lock, release, assert warning-not-exception.)

### Practical guidance

- Leave it at 300 unless the warning above appears in logs.
- Do not confuse it with AGENT_API_SESSION_TTL_MINUTES (how long an
  idle SESSION lives, default 60 minutes). Lock TTL covers one TURN;
  lock << session, always.
- It interacts with LLM timeout posture: get_llm() sets no explicit
  request timeout today, so a hung Azure call can hold a turn open
  toward the TTL. If an LLM timeout is ever added, keep
  lock TTL > (LLM timeout x retries) + tool time.
- Redis mode only; with REDIS_URL unset the variable is ignored.

### Deliberately not implemented: lock extension

redis-py supports extending a held lock (lock.extend()), which would
let a running turn heartbeat its lock and make the TTL almost
irrelevant. Left out on purpose: it adds a background moving part to
every turn, and at ~10x headroom plus a loud warning when the
assumption breaks, the simple version is the right complexity trade.
If the warning appears REGULARLY despite a generous TTL, lock
extension is the follow-up feature -- it slots into _TurnLock in
redis_state.py without touching anything else.

## 15. Local testing with redislite (no Redis install)

To exercise the Redis code path locally -- including the two-instance
behavior that is the whole point of P3.1 -- without installing or
administering a Redis server, use **redislite**. It is real Redis
delivered as a pip package: importing it starts an actual
`redis-server` subprocess on a TCP port. Because it IS Redis on the
wire, `redis_state.py` runs UNCHANGED, and a green run here means the
same code will behave identically against Azure Cache for Redis in
production. The only thing localhost cannot exercise is cross-host
connectivity (TLS `rediss://`, cluster DNS) -- a plumbing concern, not
a logic one.

### 15.1 Why redislite (and not the alternatives)

- `redis_state.py` speaks the Redis wire protocol directly --
  `SET NX PX`, `EXPIRE`, `ZADD`, and a Lua `EVAL` for the lock release.
  Any stand-in must speak that protocol, or you would be testing
  different code.
- redislite is that protocol, real: full fidelity (Lua locks, per-key
  TTL, atomic NX), pip-installable, no system package, no compiler
  (ships a prebuilt redis-server).
- NOT SQLite: not a server, not wire-compatible -- would mean
  rewriting the module and reimplementing TTL/locks in SQL.
- NOT fakeredis for THIS: it is in-process (lives inside one Python
  process), so it cannot back two separate agent instances -- exactly
  the topology being tested. fakeredis is only for the single-process
  unit tests (tests_api/test_redis_state.py).
- redislite runs the same 6.2.x line as the dev rig and any Azure
  Cache tier (no modules needed -- the whole reason the checkpointer
  is the plain-Redis RedisSaver, see section 3).

### 15.2 Start redislite as a standalone server

redislite's redis-server lives only as long as the Python process that
started it, so run a tiny long-lived host script and leave it running.
Save as `redis_host.py` in `agent-client/`:

```python
# redis_host.py -- a standalone local Redis for the P3.1 rig
from redislite import Redis
import time

srv = Redis(serverconfig={"port": "6379"})   # spawns a real redis-server
print(f"redis (redislite) up on 127.0.0.1:6379, pid {srv.pid} -- Ctrl-C to stop")
try:
    while True:
        time.sleep(3600)
except KeyboardInterrupt:
    pass
```

Run it in its own terminal (redislite is only needed HERE, not by the
agent -- it is not an agent dependency):

```bash
cd agent-client
uv run --with redislite python redis_host.py
```

Leave it running. Pick a different port if 6379 is taken (match it in
REDIS_URL below). redislite writes a small `.rdb` file next to the
script -- harmless; delete it any time for a clean slate.

Optional 10-second smoke test before wiring the agent (starts and
stops its own throwaway server):

```bash
uv run --with redislite python - <<'PY'
from redislite import Redis
import redis
Redis(serverconfig={"port": "6399"})            # background server on 6399
r = redis.Redis(host="127.0.0.1", port=6399)
assert r.ping() and r.set("k", "v", nx=True, px=1000) is True
print("redislite ok:", r.info("server")["redis_version"])
PY
```

### 15.3 Configure the agent (.env)

The agent needs no code changes -- only its `.env`. The one required
line points it at the redislite server:

```
REDIS_URL=redis://localhost:6379/0
```

Optional (has a default):

```
AGENT_API_LOCK_TIMEOUT_SECONDS=300
```

That is the entire agent-side change. With REDIS_URL set the agent
switches to Redis mode; unset (or commented) it is back to in-process
MemorySaver. Note the fail-fast contract: if REDIS_URL is set but the
redislite host is not running, the agent REFUSES to start -- so start
`redis_host.py` first.

Confirm on startup:

- log line `session state: redis at localhost:6379` (instead of the
  silent in-process default)
- `GET /health` returns `{"status": "ok", ..., "session_store": "redis"}`

### 15.4 The two-instance rig (mimics multiple AKS pods)

Three processes on one host -- one shared store, two agent instances --
is a faithful shrink of the production topology (N agent-api pods + one
Redis):

```bash
# terminal 0 -- the shared store
cd agent-client && uv run --with redislite python redis_host.py

# terminal 1 -- "pod A"     (.env has REDIS_URL=redis://localhost:6379/0)
AGENT_API_PORT=8080 uv run agent-api

# terminal 2 -- "pod B"     (same .env, same REDIS_URL)
AGENT_API_PORT=8081 uv run agent-api
```

Then the three checks that matter (curl or the web client, using the
session-create then send-message flow):

1. **Restart survival** -- create a session and have a short
   conversation on :8080, kill and restart :8080, send another message
   to the SAME session id: it continues with full context (in-process
   mode would 404).
2. **Cross-instance continuity** -- turn 1 to :8080, turn 2 to :8081,
   same session id: answer 2 reflects turn 1's context. This is exactly
   what a round-robin load balancer does in AKS; here you play the
   load balancer by hand.
3. **Turn serialization** -- fire two messages at one session
   simultaneously, one to each port: one waits for the other (the
   distributed lock), and the histories never interleave.

### 15.5 Rollback and cleanup

- Agent back to in-process: comment out `REDIS_URL`, restart the
  agent(s). Nothing else changes.
- Stop the store: Ctrl-C the `redis_host.py` terminal; delete the
  `.rdb` file it left if you want a clean slate.
- Moving to real Redis / Azure Cache later is the same one-line
  change: swap the `REDIS_URL` value (`rediss://...` for TLS). The
  code, having only ever talked to a `redis://` URL, does not know or
  care that redislite is gone.
