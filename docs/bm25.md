## 1. What a PDF actually is, and why extraction is a step at all

A PDF is not a text file. It is a bundle of DRAWING INSTRUCTIONS:
"place these glyphs at these coordinates on a page of this size."
There is no guaranteed notion of words, paragraphs, or reading order
inside -- just positioned marks. "Extracting text" means a library
(here, PyMuPDF) reverse-engineering the layout back into a string:
grouping glyphs into words, words into lines, lines into blocks, in
an inferred reading order.

Two practical consequences the codebase lives with:

- extraction is imperfect by nature (multi-column layouts, tables,
  and headers/footers can come out scrambled) -- good enough for
  search and for an LLM to read, but never byte-faithful;
- extraction costs real CPU per page, which is why re-extracting
  every PDF on every server start is a known cost (the pending P1.2
  item is exactly "stop doing that").

```python
# sample_1_pdf.py -- make a PDF, then take its text back out
import pymupdf

# build a 3-page PDF in memory; page 2 is deliberately BLANK
doc = pymupdf.open()
texts = ["Entitlements are ordered through the portal.",
         "",                                             # blank page
         "All access is revoked on the leaver's last day."]
for t in texts:
    page = doc.new_page()
    if t:
        page.insert_text((72, 72), t)
doc.save("sample.pdf")
doc.close()

# extraction: one string per page, numbering PRESERVED across blanks
doc = pymupdf.open("sample.pdf")
for page in doc:                        # iterating yields pages in order
    text = page.get_text("text").strip()
    label = text if text else "(blank -- kept so numbering survives)"
    print(f"[Page {page.number + 1}] {label}")   # .number is 0-based
doc.close()
```

Note the blank page: it stays in the list as an empty string. That
looks like a triviality and is actually a design decision -- if blank
pages were dropped, every later page number would shift, and the
agent's citations ("Source: handbook.pdf, Page 3") would point at the
wrong pages. Keep the slot, skip the indexing (section 8).

## 2. Tokenization: turning text into countable things

Search engines do not compare strings; they count TOKENS. The
tokenizer used here is deliberately tiny -- lowercase everything,
keep runs of word characters, drop the rest:

```python
# sample_2_tokenize.py
import re

def tokenize(text):
    return re.findall(r"\w+", text.lower())

print(tokenize("Entitlements are ordered through the Portal!"))
# ['entitlements', 'are', 'ordered', 'through', 'the', 'portal']

# what this tokenizer does NOT do -- and why it matters:
print(tokenize("revoke"), "vs", tokenize("revoked"))
# ['revoke'] vs ['revoked']  -- DIFFERENT tokens. No stemming: word
# forms do not match each other. BM25 can only match what tokenizes
# identically. "Remove access when someone quits" shares almost no
# tokens with "entitlements are revoked on the leaver's last day" --
# a human sees the same meaning; a lexical index sees ~nothing.
```

Hold onto that last observation: it is the precise boundary of
everything in this document, and the reason the Vector plan
([vector.md](vector.md)) exists. Lexical search is excellent at exact
terminology (IDs, acronyms, product names) and blind to paraphrase.

## 3. Ranking by hand: term frequency and rarity

Given a query, which page is most relevant? Two intuitions, both
countable:

1. **Term frequency (TF)** -- a page mentioning "delegation" three
   times is likelier about delegation than one mentioning it once.
2. **Rarity (IDF, inverse document frequency)** -- matching a rare
   word means more than matching a common one. Every page contains
   "the"; almost none contain "delegation". The rare match carries
   the signal.

```python
# sample_3_tfidf.py -- the two intuitions, hand-rolled
import math, re

def tokenize(text): return re.findall(r"\w+", text.lower())

pages = [
    "the portal handles ordering and the portal handles requests",
    "delegation lets a delegate approve on your behalf",
    "the leaver process revokes access on the last day",
]
corpus = [tokenize(p) for p in pages]
N = len(corpus)

def idf(term):
    hits = sum(term in doc for doc in corpus)
    return math.log((N + 1) / (hits + 1))     # rarer -> bigger

def score(query, doc):
    return sum(doc.count(t) * idf(t) for t in tokenize(query))

for q in ["the portal", "delegation approve"]:
    ranked = sorted(range(N), key=lambda i: -score(q, corpus[i]))
    print(f"query {q!r}:")
    for i in ranked:
        print(f"   {score(q, corpus[i]):5.2f}  {pages[i][:50]}")
```

Run it and read the scores: for "the portal", the word "the" appears
everywhere so its idf is ~0 -- it contributes nothing; "portal"
decides. TF x IDF is the classic scoring recipe, and it has two known
flaws that BM25 exists to fix.

## 4. BM25: TF-IDF with two fixes

**Flaw 1 -- TF grows without limit.** In plain TF-IDF, a page that
says "delegation" 50 times scores ~50x one that says it once. But the
50th mention adds no new evidence the page is about delegation.
BM25 SATURATES term frequency: the curve flattens (a parameter k1
controls how fast), so 10 mentions beat 2, but not by 5x.

**Flaw 2 -- long documents win unfairly.** More words = more chances
to match. BM25 NORMALIZES by document length relative to the corpus
average (parameter b), so a long rambling page needs proportionally
more evidence than a short focused one.

```python
# sample_4_bm25.py -- see both fixes in action
import re
from rank_bm25 import BM25Okapi

def tokenize(text): return re.findall(r"\w+", text.lower())

pages = [
    "delegation " * 50 + "and nothing else",            # keyword spam
    "delegation lets a delegate approve on your behalf", # focused page
    ("delegation appears once here " + "filler words " * 200),  # long + diluted
]
bm25 = BM25Okapi([tokenize(p) for p in pages])
for score, label in sorted(zip(bm25.get_scores(tokenize("delegation")),
                               ["spam x50", "focused", "long+diluted"]),
                           reverse=True):
    print(f"{score:6.3f}  {label}")
```

Run it: the spam page does score highest (it IS all about
delegation), but by a modest factor over the focused page -- not the
50x raw counting would give -- and the long diluted page comes last
despite containing the term, because length normalization taxes its
200 filler words. Those two behaviors are the entire practical
difference between BM25 and naive counting, and they are why it has
been the default lexical ranker in search engines for ~30 years.
`rank_bm25.BM25Okapi` (the library used by the server) implements
exactly this: construct with a tokenized corpus, `get_scores(tokens)`
returns one score per corpus entry.

## 5. Granularity: why the index is per PAGE

The final concept is not about the scoring function at all but about
WHAT you feed it -- and it is the single biggest quality lever
(P1.1's whole thesis):

```python
# sample_5_granularity.py -- whole document vs page as the unit
import re
from rank_bm25 import BM25Okapi

def tokenize(text): return re.findall(r"\w+", text.lower())

faq_page  = "delegation lets a delegate approve requests on your behalf"
handbook_pages = [f"chapter {i} filler about processes and portals" for i in range(29)]
handbook_pages.append("appendix: delegation rules -- a delegate may approve")

query = tokenize("delegation delegate approve")

# WHOLE-DOCUMENT corpus: 2 entries -- 30-page handbook is ONE blob
whole = BM25Okapi([tokenize(" ".join(handbook_pages)), tokenize(faq_page)])
s_handbook, s_faq = whole.get_scores(query)
print(f"whole-doc : handbook={s_handbook:.2f}  faq={s_faq:.2f}"
      f"   -> handbook {'loses' if s_handbook < s_faq else 'wins'}")

# PAGE-LEVEL corpus: 31 entries -- pages compete with pages
page_corpus = [tokenize(p) for p in handbook_pages] + [tokenize(faq_page)]
bm25 = BM25Okapi(page_corpus)
best = max(enumerate(bm25.get_scores(query)), key=lambda x: x[1])[0]
where = f"handbook page {best+1}" if best < 30 else "faq page"
print(f"page-level: best hit = {where}")
```

Run it: as one blob, the handbook's 29 filler pages DILUTE its one
relevant page (length normalization working against it -- correctly,
given what it was fed), and the tiny FAQ outranks it. Page-level, the
appendix page competes on its own and wins outright. Same scorer,
same text -- the unit decides the quality. Bonus effects: the hit now
carries a page NUMBER, the snippet comes from that page, and the
agent can read 1 page instead of 30 (the measured 40.4x tool-result
reduction).

## 7. Extraction: _extract_pages

`_extract_pages` (31) is sample 1 in production form: open the PDF,
`page.get_text("text").strip()` per page, return the LIST of page
strings -- index i holds page i+1, and blank pages stay as `""`
precisely so numbering survives (the citation argument from section
1). Failures are caught per FILE in `_build_index` (a corrupt PDF is
logged and skipped; it cannot take the index down), and a PDF whose
every page is empty -- a pure-image scan, for instance -- is skipped
with a warning: there is nothing lexical to index. (Scanned PDFs
would need OCR before this pipeline could see them -- a known
boundary, not a bug.)

## 8. Building the index: one entry per non-empty page

`_build_index` (60) runs once at construction (`DocIndex(docs_dir)` in
server.py) and does four things:

1. walks `docs_dir` recursively for `*.pdf`, sorted for determinism;
2. extracts per-page text and stores it in `self._pages[rel_path]`
   -- the SOURCE OF TRUTH that `read()` serves from;
3. builds the topic tree from the directory layout (subfolder name =
   topic, root files = "general") -- pure filesystem convention, no
   content analysis;
4. builds the BM25 corpus: for every page with text, append its
   tokens to `corpus` and its identity `(path, page_no)` to
   `self._index_keys` (85-95). The two lists are PARALLEL -- BM25
   only ever sees positions, and `_index_keys[i]` is how position i
   turns back into "handbook.pdf, page 17".

That parallel-list trick is the whole indexing architecture: BM25 is
a scoring black box over anonymous token lists; all meaning lives in
the key list beside it. Blank pages appear in `_pages` (numbering)
but never in `corpus` (no searchable content) -- both halves of the
section 1 decision, three lines apart.

## 9. Serving a query: search, snippets, and read

`search` (116) is five steps, each of which you have now built by
hand: tokenize the query (sample 2) -> `get_scores` (sample 4) ->
sort scores with their keys -> keep the top max_results with score >
0 -> dress each hit with its page number, total pages, and a snippet.

`_make_snippet` (212) answers "WHICH 300 characters of the hit page
do I show?" with a density scan: slide a 300-char window across the
page in quarter-window steps, count how many distinct query tokens
appear in each window, keep the densest. Crude, fast, and page-local
-- since P1.1 the snippet comes from the matched PAGE, so it is
relevant by construction rather than by luck.

`read` (160) is the retrieval half the index points at: resolve the
path (exact, then fuzzy -- suffix or stem match, so the LLM writing
"ordering_faq.pdf" instead of "entitlements/ordering_faq.pdf" still
lands, 151), then serve either the whole document or a parsed page
selection ("3", "2-5") with `[Page N]` markers either way. Invalid
selections return STRUCTURED errors naming the valid forms -- error
messages here are written for the LLM, which reads them and corrects
its next call (the same design as the csv side's search-size-gate
guidance, P0.md section 12).

## 10. The scale story, and where lexical search ends

Three engineering notes that complete the picture:

- **Pure-Python scoring.** `get_scores` walks every corpus entry per
  query, in Python, under the GIL. At the current corpus (dozens of
  documents -> hundreds of pages) that is sub-millisecond noise; at
  many thousands of pages it becomes measurable, which is flagged in
  PerformanceRecommendations and is one reason the AKS answer to MCP
  throughput is more replicas (aks.md section 4).
- **Rebuilt every boot.** Extraction + indexing run at startup, every
  time; nothing persists (P1.2 is the pending fix, and the Vector
  plan's DuckDB store would absorb it). At ~10 s scale today it is a
  readiness-probe concern on AKS, not a problem.
- **The lexical boundary.** Sample 2 showed it smallest: no stemming,
  no synonyms, no paraphrase -- `revoke` does not match `revoked`,
  and "remove access when someone quits" barely matches the leaver
  page. BM25's strengths (exact terminology, IDs, acronyms -- which
  an access-governance corpus is full of) are precisely a vector
  index's weaknesses, and vice versa. That complementarity is the
  entire argument for the HYBRID design in vector.md: keep this
  index, add embeddings, fuse the rankings. When you read that plan,
  everything in this document is the "BM25 half" it keeps.
